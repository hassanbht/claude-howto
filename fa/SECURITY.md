# سیاست امنیت

## بررسی اجمالی

امنیت برای پروژه Claude How To بسیار مهم است. این سند شیوه‌های امنیتی ما را و نحوه گزارش مسئولانه به Distinguished کاربر در مورد آسیب‌پذیری‌های امنیتی توضیح می‌دهد.

## نسخه‌های پشتیبانی شده

ما برای نسخه‌های زیر به‌روزرسانی‌های امنیتی ارائه می‌دهیم:

| نسخه | وضعیت | پشتیبانی تا |
|---------|--------|---------------|
| آخرین نسخه (main) | ✅ فعال | نسخه فعلی + ۶ ماه |

**نکته**: به عنوان یک پروژه راهنما آموزشی، ما بیشتر بر حفظ بهترین شیوه‌ها و امنیت مستندات متمرکز هستیم، نه پشتیبانی در 의미 سنتی. به‌روزرسانی‌ها مستقیماً به شاخه اصلی اعمال می‌شوند.

## شیوه‌های امنیتی

### امنیت کد

1. **مدیریت وابستگی‌ها**
   - تمام وابستگی‌های Python در `requirements.txt` Fix شده‌اند
   - از طریق dependabot و بازبینی دستی به‌روزرسانی منظم انجام می‌شود
   - در هر commit اسکن امنیتی Bandit اجرا می‌شود
   - از هوک‌های pre-commit برای بررسی امنیتی استفاده می‌شود

2. **کیفیت کد**
   - از Ruff برای lint استفاده می‌شود که مشکلات رایج را شناسایی می‌کند
   - از mypy برای بررسی نوع استفاده می‌شود تا از آسیب‌پذیری‌های مربوط به نوع جلوگیری شود
   - از طریق هوک‌های pre-commit استانداردها را ادغام می‌کنند
   - همه تغییرات قبل از ادغام بررسی می‌شوند

3. **کنترل دسترسی**
   - برای شاخه اصلی تنظیم محافظت شده است
   - قبل از ادغام نیاز به بازبینی است
   - بررسی‌های وضعیت باید قبل از ادغام Durch شوند
   - دسترسی نوشتن به ذخیره محدود است

### امنیت مستندات

1. **کلیدها در مثال‌ها نباشند**
   - کلیدهای API در همه مثال‌ها از پله‌نها استفاده می‌کنند
   - هرگز اعتبارنامه را هاردکد نکنید
   - فایل `.env.example` متغیرهای مورد نیاز را نشان می‌دهد
   - به خطر مدیریت کلیدlar به صراحت هشدار می‌دهد

2. **بهترین شیوه‌های امنیتی**
   - مثال‌ها الگوهای امن را نشان می‌دهند
   - در مستندات هشدارهای امنیتی برجسته می‌شود
   - به راهنمای امنیتی رسمی پیوند داده می‌شود
   - در بخش‌های مرتبط نحوه مدیریت اعتبارنامه مشخص می‌شود

3. **بازبینی محتوای**
   - تمام مستندات برای مشکلات امنیتی بررسی می‌شوند
   - راهنمای مشارکت شامل نکات امنیتی است
   - پیوندها و ارجاعات خارجی Validate می‌شوند


### امنیت وابستگی

1. **اسکن**
   - Bandit همه کدهای Python را برای آسیب‌پذیری اسکن می‌کند
   - از طریق هشدارهای امنیتی GitHub برای اسکن وابستگی‌ها استفاده می‌شود
   - بازبینی امنیتی دستی به صورت منظم انجام می‌شود

2. **به‌روزرسانی**
   - به‌روزرسانی‌های امنیتی هرچه زودتر اعمال می‌شوند
   - نسخه‌های بزرگ با احتیاط ارزیابی می‌شوند
   - تغییرات مربوط به امنیت در 수정هایлог شامل می‌شود

3. **شفافیت**
   - به‌روزرسانی‌های امنیتی در commit‌ها ثبت می‌شوند
   - فاش کردن آسیب‌پذیری به صورت مسئولانه انجام می‌شود
   - در صورت مناسب اطلاعیه‌های عمومی امنیتی منتشر می‌شود

## گزارش آسیب‌پذیری

### مسائل امنیتی که ما دنبال می‌کنیم

ما گزارش‌های زیر را خوشحالیم:

- **آسیب‌پذیری‌های کد**: آسیب‌پذیری‌ها در اسکریپت‌ها و مثال‌ها
- **آسیب‌پذیری وابستگی**: آسیب‌پذیری در بسته‌های Python
- **مسائل رمزنگاری**: هرگونه مسئله رمزنگاری در مثال‌های کد
- **نقص احراز هویت/مجوز**: مسائل احراز هویت یا مجوز در مستندات
- **خطرات فاش کردن داده**: خطرات نشت داده در مثال‌های پیکربندی
- **آسیب‌پذیری تزریق**: SQL، دستور و غیره
- **مسائل SSRF / XXE / پیمایش مسیر**

### مسائل خارج از دامنه

مسائل زیر در دامنه این پروژه نیستند:

- آسیب‌پذیری خود Claude Code (برای گزارش به Anthropic مراجعه کنید)
- مشکلات سرویس‌ها یا کتابخانه‌های خارجی (به پروژه‌های upstream گزارش دهید)
- مسائل مهندسی اجتماعی یا آموزش کاربران (連ersi با این راهنما نیستند)
- آسیب‌پذیری‌های نظری بدون PoC
- آسیب‌پذیری‌هایی که از طریق روش‌های رسمی به کتابخانه‌های وابسته گزارش شده‌اند


## چگونه گزارش دهید

### گزارش شخصی (توصیه می‌شود)

در صورت بروز مسائل امنیتی حساس، از گزارش شخصی GitHub استفاده کنید:

1. به آدرس <https://github.com/luongnv89/claude-howto/security/advisories> مراجعه کنید
2. روی "Report a vulnerability" کلیک کنید
3. جزئیات آسیب‌پذیری را پر کنید
4. موارد زیر را شامل کنید:
   - توضیح روشن از آسیب‌پذیری
   - componenteهای متأثر (فایل، بخش، مثال)
   - پیامدهای بالقوه
   - مراحل بازتولید (در صورت مناسب بودن)
   - روش‌های پیشنهادی برای رفع (اگر دارید)

**چه اتفاقی به‌عدم می‌افتد:**
- ما در حد ۴۸ ساعت دریافت را تأیید می‌کنیم
- ما بررسی و ارزیابی شدت را انجام می‌دهیم
- ما برای رفع با شما همکاری می‌کنیم
- ما زمان سفر فاش کردن را هماهنگ می‌کنیم
- اگر بخواهید، در اطلاعیه امنیتی به شما اشعار می‌دهیم

### گزارش عمومی

برای مسائل غیرحساس یا هم‌اکنون عموم):

1. یک GitHub Issue ایجاد کنید و برچسب `security` را به آن بزنید
2. شامل کنید:
   - عنوان: با `[SECURITY]` شروع شده و توضیح کوتاه
   - توضیح دقیق
   - فایل یا بخش متأثر
   - پیامدهای بالقوه
   - روش‌های پیشنهادی برای رفع


## فرآیند پاسخ به آسیب‌پذیری

### ارزیابی (در حد ۲۴ ساعت)

1. گزارش را تأیید می‌کنیم
2. از CVSS v3.1 برای ارزیابی شدت استفاده می‌کنیم
3. определя می‌کنیم آیا در دامنه است یا خیر
4. ارزیابی اولیه را به شما بازمی‌گردانیم

### توسعه (۱ تا ۷ روز)

1. ما مسیر رفع را توسعه می‌دهیم
2. ما مسیر رفع را بررسی و تست می‌کنیم
3. ما اعلامیه امنیتی ایجاد می‌کنیم
4. ما توضیحات انتشار را آماده می‌کنیم

### فاش کردن (بسته به شدت)

**شديد (CVSS ۹.۰-۱۰.۰):**
- فوراً مسیر رفع منتشر شود
- اطلاعیه عمومی منتشر شود
- گزارش‌دهنده ۲۴ ساعت قبل از فاش کردن مطلع شود

**بالاتر از حد mittleren (CVSS ۷.۰-۸.۹):**
- در حد ۴۸ تا ۷۲ ساعت مسیر رفع منتشر شود
- گزارش‌دهنده ۵ روز قبل از فاش کردن مطلع شود
- هنگام انتشار اطلاعیه عمومی منتشر شود

**متوسط (CVSS ۴.۰-۶.۹):**
- در به‌روزرسانی عادی بعدی مسیر رفع شود
- هنگام انتشار اطلاعیه عمومی منتشر شود

**کمتر از حد mittleren (CVSS ۰.۱-۳.۹):**
- در به‌روزرسانی عادی بعدی مسیر رفع شود
- با انتشار اطلاعیه般 همراه باشد


### انتشار

اطلاعیه‌های امنیتی ما شامل موارد زیر هستند:
- توضیح آسیب‌پذیری
- componenteهای متأثر
- ارزیابی شدت (نumerical CVSS)
- نسخه مسیر رفع
- راههای موقت از دست دادن (در صورت مناسب بودن)
- اشعار گزارش‌دهنده (اگر به شرط باشد)

## بهترین شیوه‌ها برای گزارش‌دهندگان

### قبل از گزارش

- **تأیید مسئله**: آیا می‌توانید پایدار بازتولید کنید؟
- **جستجوی issueهای موجود**: آیا کسی دیگر گزارش داده است؟
- **مشاهده مستندات**: آیا دستورالعمل‌های استفاده امن وجود دارد؟
- **تست مسیر رفع**: آیا مسیر پیشنهادی شما مؤثر است؟

### هنگام گزارش

- **بیش از حد مشخص شوید**: مسیر دقیق فایل و شماره خط ارائه دهید
- **سیاق وSpin ارائه دهید**: چرا این یک مسئله امنیتی است؟
- **تأثیر را بیان کنید**: مهاجم چه می‌تواند انجام دهد؟
- **مراحل را ارائه دهید**: چگونه بازتولید شود؟
- **پیشنهادات برای رفع ارائه دهید**: شما چگونه آن را اصلاح می‌کنید؟

### بعد از گزارش

- **صبر کنید**: منابع ما محدود است
- **پاسخگو باشید**: به سرعت به سوالات پاسخ دهید
- **غیرفعال بمانید**: قبل از رفع به طورعمومی فاش نکنید
- **فرآیند هماهنگ را احترام بگذارید**: بر اساس مهلت پیشرفت کنید


## هدرها و پیکربندی امنیتی

### امنیت ذخیره

- **پrophescia شاخه**: شاخه اصلی نیاز به ۲ تایید دارد
- **بررسی‌های وضعیت**: تمام بررسی‌های CI/CD باید Durch شوند
- **CODEOWNERS**: فایل‌های کلیدی بازبینی‌دهندگان مشخص دارند
- **Commit‌های امضا شده**: مشارکت‌کنندگان پیشنهاد می‌شوند

### امنیت توسعه

```bash
# نصب هوک‌های pre-commit
pre-commit install

# اجرای اسکن امنیتی محلی
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### امنیت وابستگی

```bash
# بررسی آسیب‌پذیری‌های شناخته شده
pip install safety
safety check

# یا از pip-audit استفاده کنید
pip install pip-audit
pip-audit
```

## راهنمای امنیت برای مشارکت‌کنندگان

### هنگام نوشتن مثال‌ها

1. **هرگز کلیدها را هاردکد نکنید**
   ```python
   # ❌ اشتباه
   api_key = "sk-1234567890"

   # ✅ بهتر
   api_key = os.getenv("API_KEY")
   ```

2. **به پیامدهای امنیتی هشدار دهید**
   ```markdown
   ⚠️ **نکته امنیتی**: هرگز فایل `.env` را به git اضافه نکنید.
   لطفاً به طور فوری آن را به `.gitignore` اضافه کنید.
   ```

3. **از مقادیر پیش‌فرض امن استفاده کنید**
   - اعتبارسنجی به صورت پیش‌فرض فعال است
   - در سناریوهای قابل بهکاربرد از HTTPS استفاده کنید
   - ورودی‌ها را Validate و پاکسازی کنید
   - از پرس‌وجوهای پارامتریزه شده استفاده کنید

4. **نکات امنیتی را مستند کنید**
   - توضیح دهید چرا امنیت مهم است
   - روش‌های امن و ناامن را نشان دهید
   - به منابع معتبر پیوند دهید
   - هشدارها را به وضوح نمایش دهید

### هنگام بازبینی مشارکت‌ها

1. **تأیید اینکه رازهای diploized نشدند**
   - پترن‌های رایج را اسکن کنید (api_key=، password= و غیره)
   - فایل‌های پیکربندی را بازبینی کنید
   - استفاده از متغیرهای محیطی را بررسی کنید

2. **تأیید شیوه‌های کدنویسی امن**
   - هیچ اعتبارنامه هاردکد نشده باشد
   - اعتبارسنجی ورودی صحیح باشد
   - احراز هویت/مجوز امن باشد
   - مدیریت فایل امن باشد

3. **تست پیامدهای امنیتی**
   - آیا این می‌تواند به悪 استفاده شود؟
   - بدترین سناریو چیست؟
   - آیا سناریوهای مرزی وجود دارد؟
