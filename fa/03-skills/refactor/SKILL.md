# مهارت بازسازی کد

این مهارت یک روش بازسازی سیستمندی کد بر اساس کتاب «Refactoring: Improving the Design of Existing Code» ( édition ۲) Martin Fowler است. این مهارت بر تغییرات کوچک، امن و تدریجی تأکید می‌کند و توسط تست‌های calendar محفوظ می‌شود.

> «بازسازی به \], درغیر آنکه رفتار خارجی نرم‌افزار تغییر کند، بهبود ساختار داخلی آن است.» — Martin Fowler

## اصول اصلی

۱. **حفظ رفتار**: رفتار خارجی باید یکسان باقی بماند
۲. **پیشگامی کوچک**: هر دفعه فقط تغییرات کوچک و قابل آزمایش انجام دهید
۳. **تست-محور**: تست‌های februarie ایمنی هستند
۴. **مداوم ادامه**: بازسازی یک فرآیند بلندمدت است، نه یک‌باره‌ای
۵. **تأیید همکاری**: هر مرحله نیاز به تأیید کاربر دارد

## अवलまる گردش کار

```
مرحله ۱: تحقیق و تحلیل
     ↓
مرحله ۲: ارزیابی پوشش تست
     ↓
مرحله ۳: شناسایی code smellها
     ↓
مرحله ۴: ایجاد برنامه بازسازی
     ↓
مرحله ۵: اجرا افزایشی
     ↓
مرحله ۶: بازبینی و تکرار
```

## مرحله ۱: تحقیق و تحلیل

### هدف
- درک ساختار و کاربرد کد پایگاه
- تعیین دامنه بازسازی
- جمع‌آوری زمینه نیاز‌های تجاری

### سوالاتی که باید قبل از شروع با کاربر تأیید شود
ابتدا موارد زیر را تأیید کنید:

۱. **دامنه**: چه فایل‌ها / ماژول‌ها / توابع نیاز به بازسازی دارند؟
۲. **هدف**: چه مشکلی را می‌خواهید حل کنید؟ (خوانایی، کارایی، قابلیت نگهداری)
۳. **محدودیت‌ها**: چه مناطقی نمی‌توانند تغییر کنند؟
۴. **فشار زمانی**: آیا این کار دیگر کارها را مسدود می‌کند؟
۵. **وضعیت تست**: آیا تست‌هایی وجود دارد؟ آیا می‌У분か?

### اقدام
- [ ] کد مقصد را بخوانید و درک کنید
- [ ] وابستگی‌ها و نقاط یکپارچگی را شناسایی کنید
- [ ]architecture فعلی را مستند کنید
- [ ] نشت‌های debt فنی (TODO، FIXME) را marca کنید

### خروجی
به کاربر گزارش دهید:
- خلاصه ساختار کد
- مناطق مشکل شناسایی شده
- پیشنهادات اولیه
- **درخواست تأیید برای ادامه اجرای**


## مرحله ۲: ارزیابی پوشش تست

### چرا تست مهم است
> «بازسازی بدون تست، مانند سوارتن zonder pervasive pembalutan.» — Martin Fowler

تست پیش‌نیاز **مهم** بازسازی امن است. بدون تست، به راحتی می‌توانید bug وارد کنید.

### مراحل ارزیابی

۱. **بررسی تست‌های موجود**
   ```bash
   # یافتن فایل‌های تست
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

۲. **اجرای تست‌های موجود**
   ```bash
   # جاوااسکریپت / تایپ‌اسکریپت
   npm test

   # پایتون
   pytest -v

   # جاوا
   mvn test
   ```

۳. **بررسی پوشش (در صورت وجود)**
   ```bash
   # جاوااسکریپت
   npm run test:coverage

   # پایتون
   pytest --cov=.
   ```

### نقطه تصمیم‌گیری: پرسیدن از کاربر

**اگر تست‌ها وجود دارند و به درستی اجرا می‌شوند:**
- به مرحله ۳ بروید

**اگر تست‌ها گم شده یا ناقص هستند:**
- گزینه‌ها را ارائه دهید:
  ۱. ابتدا تست بنویسید (توصیه می‌شود)
  ۲. در طول بازسازی به تدریج تست اضافه کنید
  ۳. بدون تست ادامه دهید (مخاطراتی است، نیاز به تأیید کاربر است)

**اگر تست‌ها شکست می‌خورند:**
- متوقف شوید. ابتدا تست‌های شکست‌خورده را اصلاح کنید سپس بازسازی کنید
- از کاربر بپرسید: آیا ابتدا تست‌ها را اصلاح کنیم؟

### پیشنهادات نوشتن تست (در صورت نیاز)

برای هر تابعی که قرار است بازسازی شود، تست باید موارد زیر را پوشش دهد:
- مسیر معمولی
- موارد مرزی (ورودی خالی، null، مقادیر مرزی)
- سناریوهای خطا (ورودی نامعتبر، استثناها)

از حلقه «سرمسبز-بازسازی» استفاده کنید:
۱. تست شکست‌خورده بنویسید (سرمسبز)
۲. آن را اجرا کنید (مسبز)
۳. سپس بازسازی کنید

## مرحله ۳: شناسایی code smellها

### code smell چیست؟
نشانه سطحی از مشکلات عمیق در کد. آن‌ها هرگز bug نیستند، اما نشان می‌دهند که طراحی کد ممکن است مشکل داشته باشد.

### فهرست رایج code smellها

فهرست کامل در [references/code-smells.md](references/code-smells.md) وجود دارد.

#### مرجع سریع

| code smell | نشانه | تأثیر |
|-------|------|------|
| **تابع LengthInG** | تابع بیش از ۳۰-۵۰ خط | درک، تست و نگهداری مشکل است |
| **کد تکراری** | منطق واحد در چند جا | اصلاح نیاز به تغییر در چند مکان |
| **کلاس Grand** | کلاس بیش از حد مسئولیت دارد | اصل مسئولیت واحد را نقض می‌کند |
| **Feature Envy** | یک متد بیشتر به داده‌های کلاس دیگر وابسته است | 엮ment ضعیف |
| **خود případě اسیر** | استفاده بیش از حد از کلاس‌های پایه به جای اشیاء | مفهومی قلمرو غایب |
| **لیست پارامتر Grand** | متد بیش از ۴ پارامتر دارد | صدا زدن مشکل است |
| **داده جفتی** | یک گروه داده همیشه با هم ظاهر می‌شوند | تجریدی غایب |
| **switch statements** | زنجیره پیچیده switch / if-else | در توسعه مشکل است |
| **عمومی‌سازی خیالی** | طراحی برای «در صورت نیاز آینده» قبل از زمان | پیچیدگی بی‌ notwendند |
| **کد مرده** | کد استفاده نشده | ایجاد سردرگمی و بار نگهداری |

### مراحل تحلیل

۱. **تحلیل خودکار** (در صورت وجود اسکریپت)
   ```bash
   python scripts/detect-smells.py <file>
   ```

۲. **بررسی دستی**
   - به صورت منظم کد را reviews کنید
   - هر code smell شناسایی شده را ثبت کنید
   - بر اساس شدت طبقه‌بندی کنید (Critical / High / Medium / Low)

۳. **اولویت‌بندی**
   - اولویت داده شود به مواردی که:
     - پیشرفت فعلی را مسدود می‌کنند
     - باعث ایجاد bean یا سردرگمی می‌شوند
     - در مسیرهای کد مصاحب‌تر است

### خروجی: گزارش code smell

به کاربر ارائه دهید:
- code smellهای شناسایی شده و مکان‌ها
- ارزیابی شدت هر مورد
- ترتیب اولویت پیشنهادی
- **درخواست تأیید اولویت از کاربر**

## مرحله ۵: اجرا افزایشی

### قانون طلایی
> «تغییر → تست → موفقیت؟ → commit → قدم بعدی»

### ritmo اجرا

برای هر قدم بازسازی:

۱. **پیش‌بررسی**
   - تست‌ها موفقیت‌آمیز (سبز)
   - کد قابل compil است

۲. **فقط یک تغییر کوچک انجام دهید**
   - بر اساس عملیات مشخص در فهرست اقدام کنید
   - تغییرات را به حداقل بگذارید

۳. **تأیید**
   - بلافاصله تست اجرا کنید
   - بررسی کنید خطاهای compil وجود ندارد

۴. **اگر تست‌ها موفقیت‌آمیز باشد (سبز)**
   - با پیام commit transparent commit کنید
   - به مرحله بعد بروید

۵. **اگر تست‌ها شکست بخورد (قرمز)**
   - بلافاصله متوقف شوید
   - تغییرات را undo کنید
   - دلیل را تحلیل کنید
   - در صورت سوال از کاربر بپرسید

### استراتژی commit

هر commit باید:
- **باقی‌مانده‌ناپذیر**: فقط یک تغییر منطقی داشته باشد
- **قابل undo**: به راحتی قابل لغو باشد
- **واضح توضیح داده شود**: پیام commit transparent باشد

مثال پیام commit:
```
refactor: Extract calculateTotal() from processOrder()
refactor: Rename 'x' to 'customerCount' to improve clarity
refactor: Remove unused validateOldFormat() method
```

### گزارش پیشرفت

در پایان هر زیرمرحله، به کاربر گزارش دهید:
- چه تغییراتی انجام شده است
- آیا تست‌ها همچنان موفقیت‌آمیز هستند
- چه مشکلاتی پیش آمده است
- **پرسید**: «برای دسته بعدی ادامه دهیم؟»

## دستورالعمل‌های مهم

### چه زمانی متوقف شوید و از کاربر بپرسید

در موارد زیر حتماً متوقف شوید و با کاربر تأیید کنید:
- در مورد منطق تجاری مطمئن نیستید
- تغییر ممکن است روی API خارجی تأثیر بگذارد
- پوشش تست ناکافی است
- نیاز به تصمیم kiếnشی Grand است
- ریسک بالا است
- با پیچیدگی غیرمنتظره مواجه شده‌اید

### قوانین ایمنی

۱. **بدون تست بازسازی نکنید** (مگر اینکه کاربر صریحاً ریسک را تأیید کند)
۲. **تغییرات Grand انجام ندهید**، به مراحل کوچک تقسیم کنید
۳. **بعد از هر تغییر تست راosk نکنید**
۴. **اگر تست شکست خورد ادامه ندهید**، ابتدا اصلاح یا undo کنید
۵. **فرض نکنید**، مطمئن نیستید بپرسید

### کارهای غیرمجاز

- بازسازی و قابلیت جدید را با هم ترکیب نکنید
- در زمان خطای تولید بازسازی نکنید
- کدی را بازسازی نکنید که نمی‌فهمید
- از طراحی بیش از حد دوری کنید، ساده نگه دارید
- هرگز همه چیز را یک‌باره بازسازی نکنید

## مثال شروع سریع

### سناریو: تابع LengthInG + منطق تکراری

**قبل از بازسازی:**

```javascript
function processOrder(order) {
  // ۱۵۰ خط کد، شامل:
  // - منطق اعتبارسنجی تکراری
  // - محاسبه درونخطی
  // - nhiều مسئولیت مخلوط
}
```

**مراحل بازسازی:**

۱. **تأیید وجود تست**، покриپ processOrder() را покриپ کنید
۲. **استخراج** منطق اعتبارسنجی به validateOrder()
۳. **تست** - باید موفقیت‌آمیز باشد
۴. **استخراج** منطق محاسبه به calculateOrderTotal()
۵. **تست** - باید موفقیت‌آمیز باشد
۶. **استخراج** منطق اعلان به notifyCustomer()
۷. **تست** - باید موفقیت‌آمیز باشد
۸. **بازبینی** - processOrder() اکنون فقط ۳ تابعtransparent را samen zieht

**بعد از بازسازی:**

```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```
